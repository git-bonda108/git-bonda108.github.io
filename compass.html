How a question flows

Six steps from sign-in to a cited answer.

Figures are computed in code with provenance. "Not visible to your role" and "no confident answer" are real answers, never guesses.

01Sign in

Teams, the landing zone or the web console establishes who is asking through Entra ID.

02Resolve scope

Compass maps the person to their F&O user: roles, default legal entity, store context. Admin profiles can override.

03Plan

The model picks tools under a schema; verified exemplars of similar questions guide the plan.

04Read live

Read-only OData calls to F&O, scoped to the company; knowledge retrieval over the business's own SOPs for the how-to.

05Compose honestly

Figures are computed in code; the answer names the company, cites sources and states confidence, or declines and logs a gap.

06Record

An episode (tools, checks, latency) is written for evaluation. The nightly battery and the judge read the same evidence.

Access & security

Read-only by construction. Scoped to the person, every time.

No write path exists

The Dynamics client has no write method. Write, form and action tools are never exposed and are refused by name, proven every night by the adversarial cases.

Role ∩ pack

Effective access is always the person's own F&O role intersected with the tool pack. A pack can never widen what a role allows. Finance views stay behind a deny-list.

Fail-closed doors

The landing-zone surface validates signature, tenant, audience, expiry and scope; refuses app-only tokens; accepts only the landing zone's origin; refuses anyone it cannot place as an F&O user.

Zero Trust applied

Verify every request (Entra sign-in or validated bearer, per-client API keys). Least privilege. Assume breach: external content is treated as untrusted input, never as instructions.

OWASP LLM & Agentic Top 10

A written assessment and twelve permanent adversarial cases: injection, disclosure, authority-framed writes, role escalation, PII probes, tool misuse. They run every night.

Supply chain & secrets

Pinned dependencies, dependency audit, an SBOM per build, secret scanning over history. No secrets in the repository; runtime settings live in App Service.

Evaluation harness

How well it is tested.

Evaluation-first: the battery is written before changes, gates every release, and re-runs against production every night.

Seven layers of evidence

  • Trace spineEvery answer leaves an episode: tools, retrieval, checks, latency. 3,738 recorded.
  • Release battery88 exact pass/fail cases: order tracker 28, sales 28, retail 20, adversarial 12. Nothing ships without a green run.
  • Independent judgeGrades groundedness, intent, tool accuracy, task adherence and completeness against the evidence the tools returned. Calibrated at 95% agreement with human review on a 20-case set.
  • Nightly canaryFull judged battery against production at 03:00 AEST, regression analysis against comparable baselines, a Teams card, and a red auto-files a diagnosed GitHub issue.
  • Learning loopEpisodes that pass both layers become gold exemplars retrieved as precedents at planning time. 44 verified; inspectable and deletable; no retraining.
  • Business regressionThe client's original validation workbooks re-run in production and scored with evidence: 46 / 46.
  • Unit tests24 offline tests for token validation, identity, run summaries and router accept/refuse paths, in CI on every commit.

Red nights, honestly

32 nights since 3 September: 25 green, 6 red, 1 running. Functional packs 76 / 76 green every night.

Five of the six reds were one adversarial wording case: the agent refused a write correctly, then offered to fetch. The fence held every time; the first occurrence found a real defect, fixed in v3.6.2 with a tightened no-overpromise rule. One red was a harness timeout, fixed with retry-on-exception and comparable baselines.
